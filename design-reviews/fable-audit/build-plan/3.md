### Q6 — Resolve the teal-aim-ring-on-red-wrong collision

**Where:** The wrong-answer moment — a token that has just been pressed and is showing the red `.wrong` verdict state.

**What (mockup-ready):** Suppress the teal `:focus-visible` aim/focus ring specifically when a token also carries `.wrong`, and replace it with a neutral desaturated ring at the identical geometry (same width, offset, and double-ring structure) — so keyboard focus stays visibly present and spatially unambiguous, but no longer borrows the "active/good" teal semantic. The red `.wrong` fill and ✗ glyph are untouched. Teal remains reserved for "good / active / focused" everywhere else in the system (Phantom, focus ring, EASY badge, `>` prefix); a wrong token no longer visually argues with its own verdict.

**Why:** Resolves L2-F5 (`02_findings.md` lines 194–199) and L6-F1 (lines 554–559). When a wrong token is pressed, it keeps the teal `:focus-visible` ring while simultaneously carrying the red `.wrong` fill + ✗ glyph — teal signals "good/active" everywhere else, so pairing it with a wrong-verdict token is a color-language collision; at speed the teal ring can read as "this one" while the red says "not this one." L6-F1 measures the teal-vs-red separation at only ~3.4:1, muddying which signal is primary. Independently flagged by blinded read groups 3 and 11. Serves LEARNING (removes a mixed signal that could slow or mislead recognition of a wrong answer at speed) and holds the taste anchor (keeps the system's color grammar internally consistent rather than papering over a collision).

**Player/Learner impact + Craft/Cohesion:** Wrong answers read unambiguously as wrong, with no competing "this is active/good" cue — clearer, faster recognition during fast-paced play. Tightens the game's color-semantics into strict internal consistency, closing a defect two independent blinded read groups caught.

**Accessibility note:** Outcome stays triple-encoded (✗ glyph + red fill + text) throughout — zero color-alone risk, and the ✗ glyph (the load-bearing non-color signal) is never removed; this is a consistency fix, not a color-alone breach. Preserves the existing `:focus-visible` double-ring focus/trap/restore system unchanged in geometry, width, and offset — only the hue/saturation of the ring shifts, so keyboard focus visibility is never over-corrected away. The replacement ring color must independently satisfy WCAG 2.2 SC 1.4.11 Non-text Contrast (≥3:1 against both the base background and the adjacent red `.wrong` fill) and SC 2.4.7 Focus Visible / SC 2.4.11 Focus Not Obscured; if the desaturated candidate can't clear 3:1 against both adjacent surfaces, darken/lighten it (not the geometry) until it does. No photosensitivity-timing, motion, or reduced-motion surface is touched.

**Effort:** S — presentation-only CSS color/token change on the focus-ring pseudo-class scoped to the `.wrong` state. No dependencies or conflicts with other proposals. Fence-clean: does not remap NESW swipe/arrow-key directions, does not touch the mastery rule, adds no pressure/threat mechanic, does not change the Phantom's travel/aim logic, authors no new teaching content. Protect-list clean: preserves the focus double-ring + trap/restore system, "outcome never color-alone," and the difficulty/verdict color grammar (verdict colors unchanged, only the aim/focus ring's color in this one collision state is adjusted); no touch to photosensitivity timing, the capture-lunge overshoot spring, ONE-ACTOR-MOVES, hand-authored mnemonics/decoys, byline footer, two-line title pitch, touch input handling, deck-load failure floor, the "death reframed as study report" mechanic, seeded lifetime-stats strip, "THE ANSWER IS" typography, modal keycap `<dl>`, the RM/forced-colors/aria-live layer, the synthwave-grid refusal, the favicon↔mascot geometry chain, the responsive citizens, `[EXPLAIN-TEXTCONTENT]` rendering, or `gc.v1` persist keys.

Under reduced motion: no dissolve animation exists to begin with (RM already collapses transitions to ~0), so the held green border + ✓ + command text is simply rendered as a static state for the same 750ms/1200ms window and cleared at the same M2 boundary — the static hold *is* the RM path, not a fallback bolted on. No new motion is introduced for RM; the fix is that RM finally shows something to hold rather than nothing.

The existing capture-lunge overshoot spring (the token's arrival animation into the captured slot) is untouched — this proposal adds a persistent post-lunge state layer beneath/after it, not a replacement.

**Why:** Directly resolves L3-F4 (arcade success "quiet exit," fades by 260ms vs. 1900ms of miss fireworks; annotated `assets/annotated/L3-F4.svg`), L4-F2 (RM correct-confirm "nearly invisible," vanishes at the 250ms setTimeout with no dissolve, falls between 3fps samples; annotated `assets/annotated/L4-F2.svg`), L2-F6 (opacity-0 fade leaves "three wrong answers floating in space," no lingering +points or checked card), L6-F2 (RM asymmetry: failure feedback rich and persistent, success "near-mute," disadvantages the motion-sensitive users RM exists to serve), L3-F7 (learn-mode "CORRECT!" panel never shows `card.answer`, so the winning command is only visible on a small, sometimes-clipped/wrapped token — e.g. `mv old.txt -> new.txt` rendering as garbage per `assets/motion-frames/rec-learn-moment__dark__1440/f051.png`), and L8-F3 (signature-level read: "success vanishes too fast... the correct command is gone at the exact moment a trainer should burn it in"; annotated `assets/annotated/L8-F3.svg`). It inverts the audit's core read — "failure gets fireworks, success gets a quiet exit" — without adding a single millisecond to pacing, which is fenced. It serves the LEARNING test directly: the whole point of a command trainer is that the correct string is what gets reinforced, and right now it is structurally the least visible thing on screen at the moment it matters most. It serves the taste anchor because the fix is restraint, not spectacle: no new panel chrome, no competing burst — just letting the win hold still long enough to read, the editorial equivalent of not cutting away from the answer.

**Player/Learner impact + Craft/Cohesion:** Winning finally feels like the reward the loop is built around instead of an afterthought next to the miss vignette — closes the fun asymmetry the audit calls out as the game's biggest weak point. For learning, the burned-in command closes L3-F7's gap directly: every correct answer, in both modes, now puts the literal command string in front of the player at full size, in mono, uncut — the single highest-leverage teaching moment in the whole trainer. This is also the kind of detail ("winning is authored with the same care as losing") that reads as craft to a reviewer skimming for signal, and it's cheap: no new geometry, same timing budget, same tokens already on screen.

**Accessibility note:** Not color-alone — the ✓ glyph and the burned-in command text are independent of the green border, so a colorblind player still gets a shape and legible text confirming correctness, not just hue. Reduced motion is the design center, not an afterthought: the static held state is the RM path per L6-F2 and L4-F2, with zero new animated elements introduced for RM users — this closes a WCAG 2.2 AA gap rather than opening one. No new flashing, strobing, or rapid-alternation content is introduced (photosensitivity-safe): the +N "fly" and check-hold are single, brief, non-repeating settles well under any flash-rate threshold, and under RM they don't animate at all. The existing aria-live "Correct! +N points" announcement (noted in L6-F2) is unaffected and remains the source of truth for screen-reader users — this proposal is a visual/textContent addition, not a change to that announcement.
